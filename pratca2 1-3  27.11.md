**Три самых опасных риска**

1. **R01 - ошибка в структуре хранения расписания (20).** Опаснее остальных, потому что затрагивает сразу импорт, API и все страницы расписания: если структура неправильная, придётся переделывать базу и часть API. Без исправления демо может показать неправильные пары и аудитории, а данные придётся переносить заново.
2. **R07 - нехватка времени на тестирование (16).** Пока backend и frontend разбираются с задержками, тестирование сжимается. Если ничего не делать, на демо всплывут баги входа и поиска, а исправлять их будет негде - демо на реальных данных.
3. **R05 - болезнь backend-разработчика (15).** Он один держит базу, API, импорт и уведомления. Если он выпадет, встанет вся цепочка «БД --> API --> интерфейс --> тесты», и заменить его некем.

**П2. План реагирования и контроль**

**Ситуация**

До демонстрации 10 рабочих дней. На контрольной проверке выяснилось:

1. Backend отстаёт от графика на три дня.
2. Frontend закончил интерфейс, но не может подключить его к API.
3. Тестировщик ещё не получил готовую сборку.
4. Заказчик попросил добавить экспорт расписания в PDF.
5. Разработчик базы нашёл ошибку в структуре хранения расписания.
6. Резервное копирование базы не настроено.

**Проблемы и риски**

Проблемы:

* backend отстаёт на 3 дня - срок уже сдвинут;
* frontend не может подключиться к API - работа уже стоит;
* тестировщик без сборки - проверка уже не идёт;
* ошибка в структуре БД найдена - данные уже могут лежать неправильно.

Риски:

* PDF-экспорт. Запрос уже прозвучал, но проблема ещё не наступила: пока не поздно договориться о переносе или упрощении, иначе объём вырастет и 10 дней не хватит.
* Резервное копирование не настроено. Потери данных ещё не было, но при миграции или сбое сервера её можно потерять насовсем.

Что может случиться дальше: задержка backend тянет за собой API, без API frontend стоит, тестировщик без сборки не начинает проверку, а ошибка в структуре БД может потребовать переделки. В итоге тестирование уедет на последние дни, и демо пройдёт на непроверенной системе.

**План реагирования**

|Обстоятельство|Что делаем|Кто|Срок|
|-|-|-|-|
|Backend отстаёт на 3 дня|Убираем из демо необязательное, backend сначала закрывает минимум для API|Руководитель, Backend|день 1|
|Frontend без API|Фиксируем контракт API и поднимаем mock, frontend подключается к mock, потом меняет адрес на реальный|Аналитик, Frontend|день 1–2|
|Тестировщик без сборки|Собираем промежуточную сборку на mock, тестировщик проверяет формы, валидацию и сценарии|Frontend, Тестировщик|день 3|
|PDF-экспорт|Переносим после демо, в бэклоге фиксируем как отдельную задачу; если заказчик настаивает - делаем простую печать страницы в PDF|Руководитель, Аналитик|день 1|
|Ошибка в структуре БД|Останавливаемся на исправление: сначала бэкап, потом миграция, проверка импорта на реальном файле|Backend|день 2–3|
|Нет резервного копирования|Ежедневный дамп базы и проверка восстановления из копии|Backend|день 2|

Порядок работ меняем: сначала контракт API и исправление структуры БД, потом промежуточная сборка, интеграция и только затем регресс. Параллельно идут frontend на mock, тестировщик на сценариях и аналитик на контракте.
